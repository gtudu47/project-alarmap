# Cahier des charges — AlarMap

## 1. Objectif général

**AlarMap** est un outil web de modélisation cartographique destiné principalement aux projets médiévaux-fantastiques.

Il doit permettre de créer, modifier, sauvegarder, publier et intégrer des cartes interactives comprenant notamment :

- continents ;
- océans ;
- relief ;
- rivières ;
- lacs ;
- forêts ;
- biomes ;
- royaumes ;
- provinces ;
- villes ;
- villages ;
- forteresses ;
- routes ;
- routes commerciales ;
- religions ;
- cultures ;
- langues ;
- zones magiques ;
- lieux historiques ;
- chronologie.

Les cartes devront pouvoir être consultées depuis n’importe quelle page web sans nécessiter l’installation de l’éditeur.

---

# 9. Création du fichier `.env`

Codex doit créer localement :

```text
.env
```

avec le contenu initial demandé :

```dotenv
DB_HOST=localhost
DB_USER=mon_utilisateur_postgres
DB_PASSWORD=mon_mot_de_passe_secret_123
DB_NAME=ma_base_de_cartes
```

Ce fichier sert de configuration locale initiale.

Il ne doit jamais être poussé sur GitHub.

---

# 10. Adaptation automatique de `.env`

L’installateur est autorisé à adapter automatiquement certaines valeurs.

Par exemple, dans un environnement entièrement Docker :

```text
DB_HOST=postgres
```

peut remplacer :

```text
DB_HOST=localhost
```

si `postgres` correspond au nom du service Docker PostgreSQL.

Les valeurs contenues dans `.env` doivent donc être considérées comme configuration locale de départ.

---

# 11. Mot de passe de production

La valeur :

```text
mon_mot_de_passe_secret_123
```

doit uniquement être considérée comme valeur initiale ou exemple de développement.

Lors d’une installation automatisée destinée à être réellement utilisée, l’installateur doit générer automatiquement un mot de passe PostgreSQL aléatoire fort.

Il doit également générer :

- JWT_SECRET ;
- clés API internes éventuelles ;
- secrets MinIO ;
- autres secrets nécessaires.

Aucun secret généré ne doit être envoyé dans Git.

# 12. Création de `.env.example`

Codex doit créer :

```text
.env.example
```

Ce fichier doit être versionné sur GitHub.

Il doit expliquer aux autres utilisateurs comment configurer AlarMap.

Contenu recommandé :

```dotenv
# ============================================================
# AlarMap - Exemple de configuration
# ============================================================
#
# Copiez ce fichier sous le nom :
#
# .env
#
# puis modifiez les valeurs selon votre installation.
#
# Le fichier .env contient des informations sensibles.
# Il ne doit jamais être envoyé sur GitHub.
#
# Exemple :
#
# cp .env.example .env
#
# Sous Windows :
#
# Copy-Item .env.example .env
#
# ============================================================


# ------------------------------------------------------------
# PostgreSQL
# ------------------------------------------------------------

# Adresse du serveur PostgreSQL.
#
# Installation locale :
# DB_HOST=localhost
#
# Installation Docker :
# DB_HOST=postgres
#
DB_HOST=localhost


# Nom de l'utilisateur PostgreSQL utilisé par AlarMap.
DB_USER=mon_utilisateur_postgres


# Mot de passe PostgreSQL.
#
# IMPORTANT :
# remplacez cette valeur par un mot de passe fort.
#
DB_PASSWORD=change_me


# Nom de la base de données utilisée par AlarMap.
DB_NAME=ma_base_de_cartes


# ------------------------------------------------------------
# PostgreSQL - Port
# ------------------------------------------------------------

DB_PORT=5432


# ------------------------------------------------------------
# API AlarMap
# ------------------------------------------------------------

API_PORT=3000


# ------------------------------------------------------------
# Editor
# ------------------------------------------------------------

EDITOR_PORT=4200


# ------------------------------------------------------------
# Viewer
# ------------------------------------------------------------

VIEWER_PORT=4201


# ------------------------------------------------------------
# Sécurité JWT
# ------------------------------------------------------------

# Clé utilisée pour signer les jetons JWT.
#
# Elle doit être longue, aléatoire et privée.
#
JWT_SECRET=change_me_with_a_long_random_secret


# ------------------------------------------------------------
# URL publique
# ------------------------------------------------------------

PUBLIC_APP_URL=http://localhost


# ------------------------------------------------------------
# Mise à jour automatique
# ------------------------------------------------------------

# Active ou désactive le système de mise à jour automatique.
AUTO_UPDATE=true


# Branche GitHub suivie par l'updater.
#
# La production doit utiliser main.
#
INSTALL_CHANNEL=main


# ------------------------------------------------------------
# Stockage S3 / MinIO
# ------------------------------------------------------------

S3_ENDPOINT=http://localhost:9000
S3_BUCKET=alarmap
S3_ACCESS_KEY=change_me
S3_SECRET_KEY=change_me


# ------------------------------------------------------------
# Environnement
# ------------------------------------------------------------

NODE_ENV=production
```

# 14. Installation en une commande

L’utilisateur doit pouvoir installer AlarMap depuis GitHub avec une seule commande.

Windows :


```bash
curl -fsSL https://raw.githubusercontent.com/OWNER/AlarMap/main/install.sh | bash
```

Les URLs seront remplacées par celles du dépôt définitif.

# 70. Zones d’influence religieuse

Chaque religion peut posséder une ou plusieurs zones d’influence géographique.

Exemple :

```typescript
interface ReligionRegion {
    id: string;
    religionId: string;
    geometry: GeoJSONGeometry;

    influenceLevel?: number;
    majority?: boolean;

    startYear?: number;
    endYear?: number;
}
```

Le niveau d’influence pourra par exemple utiliser :

```text
1 = présence marginale
2 = minoritaire
3 = importante
4 = majoritaire
5 = religion dominante
```

Les zones doivent pouvoir se chevaucher.

Cela permet de représenter des régions où plusieurs religions coexistent.

# 73. Importance des lieux saints

# 74. Lieux saints partagés

Cela est obligatoire pour permettre :

- sanctuaires partagés ;
- villes saintes contestées ;

- anciens sanctuaires réutilisés par une autre religion.

# 86. Tolérance politique et religieuse

Un royaume pourra avoir une politique envers chaque religion.

Exemple :

```typescript
interface KingdomReligionPolicy {
    kingdomId: string;
    religionId: string;

    status:
        | "state_religion"
        | "official"
        | "recognized"
        | "tolerated"
        | "restricted"
        | "forbidden"
        | "persecuted";
}
```

Cela permettra à la carte de distinguer :

```text
relation entre religions
```

de :

```text
politique d’un État envers une religion
```

Ces deux concepts ne doivent pas être confondus.
